# 中国国际象棋棋手数据库第二轮复审修改意见

> 日期：2026-07-18  
> 基线：`main@36a7280b5f`  
> 范围：上一轮代码复审后仍未解决的事项，以及本轮确认的身份认定与前端展示规则  
> 性质：待修改清单，不重复已经完成的历史建议

## 1. 结论与优先级

当前产品结构已经比初版方案简洁，公共来源字段清理、旧 dashboard/排行榜实现、旧 local-data-center 页面和部分重复脚本等已完成项不再列为待办。本文件只保留仍会影响数据正确性、身份展示和发布一致性的修改意见。

建议按以下顺序处理：

1. 修正 PGN 归档识别、配对匹配和“应有棋谱”分母。
2. 修正快照原子性，保证线上所有 manifest 属于同一 snapshot。
3. 上线高置信展示身份组，使前端默认按同一棋手呈现，同时保留质疑即拆分。
4. 补齐身份否决记录、PGN 人工补件入口和核心机制测试。
5. 最后再推进参考估分及同年龄、同出生年排名。

## 2. PGN 与赛事完整性

### 2.1 直接消费赛事 PGN 归档，不能只依赖 by-player 索引

当前 `Scripts/build_completeness_report.py` 主要从 `docs/data/index/by-player/` 建立棋局匹配索引，没有把 `data/generated/chess-results-event-pgn/` 中的逐赛事归档作为第一等输入。因此“已有完整 PGN，但尚未生成 by-player 关联”会被错误判断为“归档不完整或需要重新抓取”。

已确认的反例是 `tnr1266792`：

- 排除轮空后有 306 盘实际对局；
- 本地赛事归档正好有 306 盘 PGN；
- 当前完整性报告却得到 `matchedPairings=0`，并将其列入 P0 重新抓取/重新匹配队列。

修改要求：

- 建立统一的 `GameObservation` 索引，输入至少包括逐赛事 PGN、by-player PGN 包和 Lichess 对局；
- 抓取状态与匹配状态分开：`not-published`、`fetch-failed`、`archived-unmatched`、`matched-partial`、`matched-full`；
- 已存在赛事 PGN 时优先做离线解析和匹配，不得引导维护者重新访问来源。

验收：`tnr1266792` 能在不重新抓取的情况下识别为 306/306，并从补抓队列移除。

### 2.2 使用赛事自然键匹配，姓名只能作为回退证据

当前匹配键近似为“轮次 + 排序后的双方姓名”，会丢失台次、颜色和 `playerNo`，存在同名错配、反色错配和错误计算完整率的风险。

主匹配键应为：

```text
sectionID + round + board + whitePlayerNo + blackPlayerNo
```

FIDE ID、执白/执黑姓名、结果和规范化 PGN 指纹用于校验与回退。回退匹配必须输出原因和置信等级，不得静默算作精确匹配。

### 2.3 区分“有赛果”和“实际开局”

当前 PGN 分母只排除轮空，没有排除弃权、取消或未实际开局的对局。`tnr1437536` 的 117 条非轮空配对中有 2 盘为弃权结果，实际应有 PGN 为 115 盘；现有报告因此把完整的 115 盘误标为 98.29% 部分覆盖。

为每条 Pairing 增加 `playedGameExpected`：

- 正常完赛：`true`；
- 轮空、单方弃权、双方弃权、取消、未开局：`false`；
- 无法判断：`unknown`，不得直接进入完整分母。

赛事结果完整性可以接受合法弃权结果，但 PGN 完整性只能以 `playedGameExpected=true` 为分母。

### 2.4 完整性门禁必须具有独立 expected 值

当前部分门禁使用 `expected=actual=len(currentData)`，只能证明文件内部自洽，不能证明名单、排名和轮次确实抓全。

修改要求：

- 轮数来自赛事元数据或已核验的轮次清单；
- 名单、排名、配对分别做 `playerNo` 引用完整性检查；
- 每轮期望台数结合参赛人数、轮空和退赛状态计算；
- `resultsComplete` 必须实际消费每一道门禁，不能只检查 standings 非空；
- 无法获得独立 expected 时标成 `unknown`，不能冒充 `complete`。

### 2.5 PGN 补件队列只保留真实可行动任务

当前队列包含大量没有任何 PGN 线索的普通 `not-published` 赛事，同时遗漏没有 event-detail、但已有本地分包或人工线索的盐城快棋赛。

修改要求：

- 没有公开 PGN 线索的赛事只进入覆盖统计，不生成逐场待办；
- 有本地归档但匹配失败：P0 离线修复；
- 有部分直播棋谱：P1 补齐或确认公开范围；
- 维护者明确知道曾有全台 PGN、但当前缺包：P1 人工补件；
- 新增私有 `pgn-leads` 登记表，记录赛事、组别、线索类型、已知覆盖和处理状态；
- 提供维护者私有文件上传/导入路径，公共贡献页仍不允许社区客户端回抓来源。

盐城快棋赛 `tnr1210265`–`tnr1210272` 应作为首批补件样例：先合并现有 6 个组别的棋手分包，再人工补入缺少的 2 个组别，最后按逐轮配对验收。

## 3. 快照、构建和发布

### 3.1 缺输入不能以成功状态保留旧产物

部分 builder 在私有输入缺失时返回 0 并保留旧输出，顶层 snapshot 构建因此把“跳过且沿用旧文件”误记为成功。线上曾同时出现：

- 根 snapshot/API：`20260718T030759Z-46b7183c`；
- event-details manifest：`20260718T024713Z-a8648a71`。

修改要求：

- builder 返回结构化的 `built/skipped/failed`；
- required layer 被跳过时，顶层构建失败；
- 发布前校验所有公开 manifest 的 `snapshotId`；
- 只有校验全部通过后才原子切换根 snapshot；
- 旧快照可整体保留，但不能与新快照混合引用。

### 3.2 调整身份构建顺序并保存机器审计产物

当前国内身份同步早于 `PersonObservation` 生成，新赛事的身份候选会滞后一轮；构建流程还调用不存在的 `build_identity_candidates.py`。CI 只提交 `docs/data` 和 `docs/api`，完整性报告、身份候选、等级分观察等 `data/generated` 产物没有进入可复现发布状态。

建议顺序：

```text
CompletenessReport
→ PersonObservation
→ identity candidates / PresentationIdentityGroup
→ domestic projection
→ player/event indexes
→ API and snapshot validation
```

删除不存在的构建步骤。通过 release manifest 明确哪些机器审计产物需要持久化；不适合公开仓库的原始身份候选应保存到仓库外维护工作台，而不是在构建后直接丢弃。

### 3.3 公共 manifest 只列公共可访问资源

国内棋手 manifest 当前仍可能列出 `data/generated` 内部路径以及已经迁移的 promotion-review 旧路径。公共 manifest 应只暴露真实部署的 API/静态资源；维护者审计路径放进独立 private build manifest。

## 4. 身份认定与前端默认聚合

### 4.1 永久身份与展示身份分成两层

采用两个不同实体：

| 层级 | 作用 | 写入条件 |
| --- | --- | --- |
| `IdentityLink` | 永久 canonical 身份、重定向、registry 关联 | 维护者人工确认，可撤销、可追溯 |
| `PresentationIdentityGroup` | 搜索和档案中的默认同一人展示 | 机器高置信规则自动生成，用户质疑即拆分 |

展示组不能覆盖 Person、删除原始 observation、反写 registry 或冒充人工确认。每条赛事、对局和估分输入仍保留原成员 ID，因此展示组可以无损合并和拆分。

### 4.2 “同俱乐部 + 晋级轨迹”直接属于高置信

不再要求这一组合必须额外具备出生年等强证据才进入高置信。以下条件同时成立即可判为 `suggested-high`：

1. 规范化姓名一致或属于已审核别名；
2. 俱乐部一致；
3. 前一赛事在低一级组取得至少 65% 得分率；
4. 后续赛事出现在显式相邻的高一级组，例如 `一级组 → 候补组 → 公开组`；
5. 性别一致，且没有同一时间不同组并发参赛、已核验出生年冲突等硬冲突。

俱乐部和由俱乐部推导出的地区不需要重复计分，但这不影响“俱乐部一致 + 真实晋级模式”本身被判为高置信。赛事先后必须能由实际日期确定；只有年份、无法判断先后的记录不触发自动展示聚合。

### 4.3 前端默认向“同一身份”靠拢

达到上述高置信规则后，前端不再向普通用户展示多个近似重复棋手：

- 搜索结果合并成一张棋手卡；
- 多个成员 ID 默认打开同一个聚合档案；
- 赛事时间线、对局列表、可用统计和参考估分输入按展示组聚合；
- 页面以低打扰方式标记“身份暂定，可纠错”，不展示内部权重；
- 原成员 ID、事实归属和旧深链接全部保留。

官方 FIDE 等级分始终来自 registry。展示组上的参考估分应记录 `identityBasis=presentation-high`；展示组拆分后重新计算，不能沉淀成官方事实。

### 4.4 用户质疑优先于继续聚合

聚合档案提供“这不是同一位棋手”入口。收到包含明确对象的质疑后：

1. 展示组进入 `disputed`；
2. 下一次公共投影立即恢复分开展示；
3. 维护者审核为确认合并、继续分离或负链接；
4. 质疑成立后写入 pair hash tombstone，防止同一算法建议反复聚合。

质疑入口需要限流、记录提交时间和理由，防止恶意重复拆组，但不要求用户先提供达到永久身份认定标准的强证据。

### 4.5 多人同名簇和互斥关系

三人以上同名簇先建立候选图并删除硬冲突边：

- 高置信边之间没有互斥关系时，可以形成一个展示组；
- 同一成员同时属于多个互斥方案时，保持分卡并进入维护者队列；
- 已拒绝、已质疑成立或存在硬冲突的边不得重新生成展示组；
- 任何情况下都不能仅凭传递闭包绕过一条硬冲突边。

### 4.6 身份审核数据的公开边界

俱乐部、候选边和未成年人参赛轨迹可以用于机器判断及维护者审核，但原始候选文件不应作为公开仓库大文件长期提交。公共前端只显示合并后的必要事实和纠错入口；原始证据卡、否决记录及算法调试信息保存在私有审核区。

## 5. 前端仍需修改的事项

### 5.1 完整性文案必须来自明确状态

不能因为存在 event-detail 就显示“完整赛事覆盖”或“查看赛事与棋谱”。页面应消费：

- `resultsComplete`；
- `pgnAvailability`；
- `pgnCoverage`；
- `eventComplete`。

推荐文案只使用“赛果完整”“无公开棋谱”“部分直播台棋谱”“全台棋谱”“棋谱待匹配”“抓取失败”等可核验状态。

### 5.2 删除重复的赛事目录请求状态

当前两套事件目录请求实际读取同一 `public-events.json`，所谓 full catalog fallback 不会扩大覆盖。保留一套 catalog state、缓存和错误处理即可。

### 5.3 国内棋手搜索分片按需加载

国内棋手搜索数据 gzip 后仍较大，页面启动后立即后台加载会占用移动网络。建议按姓氏/拼音首字母或哈希分片，只在输入中文姓名、拼音或打开 domestic 深链接时加载相应分片。

## 6. 对象存储与估分基础数据

### 6.1 R2 上传不能只按文件大小判定成功

上传器当前遇到同大小对象就跳过，不能发现同大小损坏文件。release manifest 已有 SHA256，应把 checksum 写入对象元数据或上传回执，并在发布后抽样/全量校验远端对象哈希。

### 6.2 RatingObservation 使用榜单生效日期

等级分历史不能按脚本运行月份归档。每条 observation 至少保存：

- FIDE list/effective date；
- 原始 registry hash；
- 抓取时间和生成时间；
- standard/rapid/blitz 控制类型。

在这些锚点稳定前，不发布基于错误月份的成长曲线或估分回测结论。

## 7. 必须新增的测试

现有测试虽然全部通过，但没有覆盖本轮最重要的机制。至少增加：

1. 逐赛事 PGN 已存在、by-player 未生成时仍能完整匹配；
2. 同名棋手、反色和同轮不同台次不会错配；
3. 轮空、弃权、取消不进入 PGN 应有分母；
4. advertised 部分台次必须逐台验证，不能只比较总数；
5. 任一公开 manifest 的 snapshotId 不一致时构建失败；
6. “同俱乐部 + ≥65% 后升组 + 无硬冲突”生成高置信展示组；
7. 并发参赛、性别/出生年冲突阻止展示聚合；
8. 用户质疑后展示组拆分，负链接阻止下一轮重新聚合；
9. 展示组合并和拆分不修改 registry、Person 与原始 observation；
10. 展示组拆分后参考估分和排名投影可重新计算。

## 8. 本轮明确不再重复的已完成项

以下内容已在当前代码中处理，不应继续出现在新的修改清单：

- 旧 dashboard、旧排行榜和无调用前端函数的大规模删减；
- `events.html` 内联事件逻辑迁移；
- 旧 local-data-center 页面和相关公开入口清理；
- 旧 youth leaderboard 双写清理；
- 公共 Chess-Results 来源字段/外链清理及校验；
- Lichess 许可和署名保留；
- 官方等级分与未来参考估分分轨。

历史产品方案可以作为决策背景保留，但后续实施、验收和 issue 拆分应以本文件的当前待办为准，不再从旧删除清单重复派生任务。
