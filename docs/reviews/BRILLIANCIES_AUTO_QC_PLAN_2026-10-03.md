# 实战妙手自动质控与上线方案

日期：2026-10-03。本文是设计方案，尚未启用自动发布。

## 核心原则与现状

**质控对象是局面和着法。**赛事、棋手、FIDE ID 是棋谱附带的事实与展示信息，不是妙手质量分。没有 FIDE ID、内部赛事 ID，甚至双方都没有 FIDE ID，均不能使局面失去复核或上线资格。不得为了凑元数据而推断身份；不能确认的备注就省略或如实标注。

已完成的历史队列覆盖 52,372 局，产生 59,318 个牺牲着法候选，按当前完整 FEN 与 UCI 着法去重后为 58,353 个局面着法组合。全部 59,318 个候选都有 PGN `Event` 名称；57,028 个 `event.id=event-unknown` 只是 PGN 没有 `TournamentID`/`EventID` 标签，并非“赛事不明”。31,574 个双方均无 FIDE ID。15,709 个候选的实战下一着在弃子落点接受了牺牲；其余不能据此判为非妙手，拒吃也可能是最佳防守。原规则仅筛出可被合法吃掉的棋子着法、引擎前两选择及着后优势；当前 `classification.symbol=!!` 是**未经最终质控的暂定候选标签**，不得直接公开为结论。

## 全量自动质控

所有候选都进入同一局面质量队列；重复局面可共用昂贵的引擎计算，但每条 PGN 实战证据与结果都须核对并保留。流程必须可续跑，按候选 ID、PGN 哈希、局面键、规则版本记录已完成步骤，升级规则只重做受影响的局面计算，不重扫已完成棋局。

1. **原局真实性**：以认证的内容寻址 PGN 重放合法着法，核对指纹、初始 FEN、`ply + UCI + SAN`、候选局面与实际续着。非法、错位或找不到原局的候选隔离；这检验的是棋局真实性，与棋手或赛事 ID 有无无关。
2. **牺牲是否成立**：枚举对手的合法接受着和最强拒吃着，分别向后分析至战术局面稳定。普通兑子、立刻等价回吃、没有实际让子或没有补偿的伪牺牲淘汰。实战是否吃子只影响“实战进程”描述，不是准入条件。真正的牺牲可由引擎变化证明，即使对手在实战中选择拒吃。
3. **棋艺质量复核**：固定 Stockfish 版本、二进制哈希、线程、哈希表、节点数和规则版本，对候选着做强制根搜索，对最佳防守、接受牺牲、关键替代着分别搜索，再用另一引擎版本或独立配置交叉检查。检验候选着的稳定性、补偿/胜率、替代着差距、非平凡性与战术解释；不能仅凭 `cp >= 80`、MultiPV 前两名或“弃后”主题给 `!!`。多条近似等价妙手允许存在，所谓唯一最佳着不能成为绝对门槛。明显已胜、简单强制将杀或普通战术须降级；守和妙手今后扩展检测时也不应被“着后必须胜势”排除。
4. **质量分层**：`S` 为跨引擎稳定、牺牲清晰、最强防守下仍有深刻战术理由的顶级 `!!`；`A` 为同样可复算且达到公开标准的 `!!`；`B` 为有潜力但计算不稳定、补偿边界或解释不足者，优先追加算力，仍不公开标 `!!`；`C` 为合法但普通的弃子/兑子；`D` 为伪牺牲或原局错误。批次按 `S → A → B` 的棋艺置信度推进，主题多样性仅用于抽样与展示，FIDE ID 和内部赛事 ID 不参与评分。只有 `S/A` 自动获批，`B` 经加深复核可升级；不设置发布数量配额。
5. **备注与权利**：PGN `Event` 名称作为赛事备注可保留；内部赛事 ID 仅用于能确定时的站内链接。棋手有 FIDE ID 时以 registry 主档为准，无 ID 时可使用经清洗的 PGN 署名但不虚构主档或身份链接；姓名不可靠时只显示“白方/黑方”。日期、轮次等缺失就不展示。公开仍须满足原 PGN 许可、署名、隐私及快照门禁；真实的许可不明单独记为发布障碍，不降局面质量等级。Lichess Broadcast 的 CC BY-SA 4.0 署名须随公开项保留。

同一质量规则产生结构化证据：输入快照/PGN 哈希、规范化局面键、着法、原局重放结果、合法接受着、最佳拒吃着、关键变化、搜索配置/二进制哈希、稳定度、等级、缺失备注与拒绝原因。公开文字仅依据已核实的事实生成，分别标注实战续着与引擎变化，不宣称机器评定为普遍公认的棋注。

## 数量预估与校准

当前可以确认的处理母数是 **59,318 个候选，至少 58,353 个不同的完整 FEN+着法组合**，而不是按身份过滤后的 1,986 个。现有统计没有计算深层真假牺牲、最佳防守和跨引擎稳定性，因而无法据此宣称已有多少个真正的 `!!`。工程容量先按 `S/A` 占去重局面的 **5%–15%** 规划，即约 **2,900–8,800 个可公开局面**；这是待验证的区间假设，不是实测合格率或上线承诺。顶级 `S` 预计只是其中一小部分，不能由现有字段精确预测。

上线前先从全部候选按主题、评估区间、棋步阶段、实战接受/拒吃状态做**加权分层随机抽样**，至少 600 个局面跑完整质控，保留各层权重、通过率和置信区间；再用样本率投影全库 `S/A/B/C/D` 数量并据此修正预算。抽样分层全部围绕棋艺和复核难度，不按 FIDE ID 或内部赛事 ID 划准入池。其后全库逐条复核，不因预测数量达到目标而停扫。

## 运行位置与工期

历史质控在维护者本机运行，直接读取已完成的两个加密历史检查点；只向 R2 上传版本化质控结果和断点，不重复扫描 52,372 局 PGN。先以两个进程处理质量抽样，再根据内存、温度和实测速度决定是否提高并行度。现有 GitHub Actions 继续只跑新入库候选筛选；新增自动质控待实现后接入同一增量链。历史全库不转到 GitHub runner。代码、规则测试与发布链仍由 GitHub CI、统一重建和部署验收。

现有历史候选筛选从 2026-09-30 12:23 至 2026-10-03 14:02，约 74 小时，包含中途 R2 断连重试。本机 Stockfish 16 标准短基准约 197 万节点/秒（单进程；不代表复杂局面的持续吞吐）。完整质控尚未实现，也没有每局面实测耗时；以每个去重局面总共约 1,000 万至 2,000 万节点、两个本机进程及上传/长尾开销粗估，600 局面试跑约 **2–8 小时**，全库约 **5–10 天**。这是排程估算，不是完成时限；必须在抽样后按实际节点、吞吐、通过率和断点开销更新剩余时间。持续增量只处理新增候选，通常跟随现有每四小时 GitHub 任务批次，但是否当批完成取决于新增量和运行时预算。

## 发布链与产品呈现

- 历史 59,318 个候选由本机离线质控；新增候选由云端自动增量质控。两者使用相同的版本化规则、局面去重与发布器，不重新抓 Chess-Results/FIDE，也不重扫已完成棋局。若云端算力不足，云端可只负责筛选和入队，复杂案例由本机批量复核并上传已验证结果。
- 机器批准项写入独立的生成层及精确 manifest/回执，不写入人工精选文件。人工撤回/勘误表拥有最终否决权但无需逐条审核。发布仍遵守 staging、基线验证、统一重建、R2 认证、部署和线上快照链；main 前进时拒绝旧基线，不强推。
- `build_brilliancies.py` 合并人工精选与机器批准，保持既有 API ID、列表、详情、PGN 和 410 撤回语义。增加 `reviewMethod: automatic`、质控版本、质量层级与可公开的证据摘要。前台统一称“ChessDB 自动质控通过的实战妙手”，先展示 `S`，再展示 `A`；同局允许多个真实妙手，列表可按多样性排布。`B/C/D` 不在前台充数。
- 不为每个条目生成独立 Pages 文件；通过项以少量分片对象供 API 按 ID 提取，保留 `/brilliancies` 共用页面。每批测量 Pages 文件数、总字节、单文件大小和 R2 配额，超限则暂停发布。每日或若干通过项合并一次部署，无变化不重建。
- 每批自动验收原局跳转、PGN、API、署名、撤回和线上快照；后续复核失败、原档失效或权利状态变化时自动撤回并保留 ID。发布异常立即停发且由旧快照继续服务。
